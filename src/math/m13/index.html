Act I — From Olympiad Contests to Trusted Kernel Infrastructure

On 16 September 2026, XTX Markets announced the closure of the AI Mathematical Olympiad (AIMO) Prize after awarding roughly $1.62 million across AIMO 1–3 and its Proof Pilot. Rather than stepping back from automated mathematics, the announcement reallocated funding directly into foundational infrastructure: $10 million toward the Lean Focused Research Organization through 2030, $10 million toward the Mathlib Initiative through 2030, and targeted open research competitions through the Scientific AI Research (SAIR) Foundation—starting with a challenge devoted directly to the Lean Kernel itself.

In Plain Words · Extra-Easy Explanation

Think of the difference between drafting an architectural skyscraper on napkins and checking its structural steel tolerances at the city permit office. A proof assistant like Lean 4 has two completely different jobs. The front end—tactics, autocomplete, neural proof search, and human hints—acts like a creative studio sketching thousands of candidate ideas. The back end, called the kernel, is an austere, tiny referee that sits behind locked doors and checks every single logical brick against the core rules of type theory. You do not have to trust the creative studio, and you do not have to trust the AI that wrote a proof draft, because nothing becomes a theorem until the kernel checks the final proof term from first principles. The catch is speed: if the studio asks the kernel to unfold a slow step-by-step calculation across thousands of tiny increments, the referee stalls even when the math is valid.

Modern dependent type theory gives mathematicians an unusually clean division of labor known as the de Bruijn criterion. In Lean 4 (de Moura & Ullrich, 2021, DOI DOI 10.1007/978-3-030-79876-5_37 [Scite ↗]), elaboration, metaprogramming, type-class resolution, and external tactic automation compile mathematical scripts down into explicit terms in the Calculus of Inductive Constructions. Those terms are then handed to a compact, C++-based type-checking kernel that validates typing judgments Γ ⊢ t : T and universe constraints without trusting any part of the frontend elaborator. Because every definition, lemma, and automation script in mathlib (DOI DOI 10.1145/3372885.3373824 [Scite ↗]) funnels through this narrow choke point, kernel performance and kernel auditability quietly govern the pace of large-scale formalization across the entire ecosystem. Whenever human or AI provers scale up to heavy algebraic, combinatorial, or number-theoretic arguments, definitional equality testing inside the kernel becomes a central bottleneck. Naive unary Peano arithmetic represents an integer n as n nested successor constructors S(S(...S(0)...)), so testing two intermediate values or unfolding recursive equations directly inside the kernel forces linear or quadratic term reductions. Work by Samuel Boutin (1997, DOI DOI 10.1007/bfb0014565 [Scite ↗]) on proof by reflection and by Benjamin Grégoire and Xavier Leroy (2002, DOI DOI 10.1145/581478.581501 [Scite ↗]) on compiled strong reduction demonstrated how type-checking kernels can evaluate computational subgoals orders of magnitude faster without sacrificing foundational soundness. The SAIR Lean Kernel Challenge (competition.sair.foundation) brings renewed focus to this exact interface between kernel simplicity, fast normalization, and adversarial proof-term resilience.

Why does kernel design matter well beyond academic proof assistants? Any organization that hopes to check machine-generated proofs—whether for cryptographic protocols, theorem libraries, or algebraic identities—faces an acute asymmetry: generating candidate proofs by search or neural sampling is messy and fallible, whereas checking a finished proof object should be fast, deterministic, and independent of the generator. If a proof kernel grows bloated with unverified shortcuts, a single reduction bug compromises every theorem checked by it. Conversely, if the kernel stays strictly minimal yet takes seconds or minutes to reduce computational subterms, automated proof synthesis hits a throughput wall. Balancing a minimal trusted computing base against logarithmic algorithmic reduction is one of the defining engineering challenges of formal mathematics in 2026.

      #!/usr/bin/env python3
"""Deterministic kernel reduction benchmark for Folio M.13: SAIR Lean Kernel Challenge.

Compares O(log n) binary fast-doubling modular Fibonacci reduction against an O(n)
iterative Peano-step reference for n = 1024 modulo 1_000_000_007, checking recursion
depth, multiplication step budget, and value identity. Passing --planted-defect
corrupts the fast-doubling recurrence sign so the reduced value diverges from the
linear reference.
"""
from __future__ import annotations

import argparse
import json
import sys


MOD = 1_000_000_007


def fast_doubling_fib(n: int, mod: int = MOD, defect: bool = False) -> tuple[int, int, dict[str, int]]:
    """Return (F_n mod, F_{n+1} mod, stats) tracking recursion depth and modular muls."""
    stats = {"depth": 0, "muls": 0}

    def _rec(k: int, cur_depth: int) -> tuple[int, int]:
        if cur_depth > stats["depth"]:
            stats["depth"] = cur_depth
        if k == 0:
            return (0, 1)
        a, b = _rec(k >> 1, cur_depth + 1)
        two_b = (2 * b) % mod
        term = (two_b + a) % mod if defect else (two_b - a) % mod
        c = (a * term) % mod
        d = ((a * a) + (b * b)) % mod
        stats["muls"] += 3
        if k & 1:
            return (d, (c + d) % mod)
        return (c, d)

    fn, fn1 = _rec(n, 1)
    return fn, fn1, stats


def linear_peano_fib(n: int, mod: int = MOD) -> tuple[int, int]:
    """O(n) unary successor reference computing F_n mod."""
    a, b = 0, 1
    steps = 0
    for _ in range(n):
        a, b = b, (a + b) % mod
        steps += 1
    return a, steps


def verify(n: int = 1024, planted_defect: bool = False) -> tuple[bool, dict[str, object]]:
    fast_val, _, stats = fast_doubling_fib(n=n, mod=MOD, defect=planted_defect)
    ref_val, peano_steps = linear_peano_fib(n=n, mod=MOD)

    matches_reference = fast_val == ref_val
    depth_ok = stats["depth"] == n.bit_length() + 1
    muls_ok = stats["muls"] <= 3 * n.bit_length()
    ok = matches_reference and depth_ok and muls_ok

    payload: dict[str, object] = {
        "folio_id": "M.13",
        "status": "PASS" if ok else "FAIL",
        "n": n,
        "mod": MOD,
        "fast_doubling_value": fast_val,
        "linear_reference_value": ref_val,
        "matches_reference": matches_reference,
        "recursion_depth": stats["depth"],
        "modular_multiplications": stats["muls"],
        "unary_peano_steps": peano_steps,
        "step_speedup_ratio": round(peano_steps / max(1, stats["muls"]), 2),
        "planted_defect": planted_defect,
    }
    return ok, payload


def main(argv: list[str] | None = None) -> int:
    parser = argparse.ArgumentParser(description="Verify binary reflection vs unary Peano reduction for Folio M.13.")
    parser.add_argument("--n", type=int, default=1024, help="Fibonacci index (default: 1024)")
    parser.add_argument("--planted-defect", action="store_true", help="Corrupt fast-doubling recurrence sign.")
    args = parser.parse_args(argv)

    ok, payload = verify(n=args.n, planted_defect=args.planted_defect)
    print(json.dumps(payload, indent=2))
    return 0 if ok else 1


if __name__ == "__main__":
    raise SystemExit(main(sys.argv[1:]))
